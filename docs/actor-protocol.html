Ensemble · Architecture spec

A persona is a spec. The runtime is who's at the controller.

Define the protocol once, plug in any backend — OpenAI, local LLM, a human, a Claude Code session, an arbitrary external agent. The session orchestrator doesn't know who's behind the connection.

Draft v0.1 · last updated 2026-05-12

§0Premise

A persona is a specification, not an implementation. The same persona can be played by an OpenAI chat completion, by a local llama.cpp, by a human typing in a textbox, by a Claude Code session, or by an arbitrary external agent we haven't built yet. Ensemble is the session orchestrator — it brokers turns between actors over a defined protocol and doesn't care what's behind the connection.

The image to hold in your head: "Waiting for Claude to join as player one." A casting lobby. Seats fill in as runtimes connect.

§1The three layers

Layer 1

Persona

Declarative spec. Name, system prompt, role hint, voice signature, tools allowed, memory policy, buzz-in policy.

Lives in your library, portable across sessions.

Lifecycle: persistent. One persona, many sessions.
Layer 2

Actor

A persona instantiated for a session. Binds Persona × Runtime × Session × Seat. Has memory scoped to the persona's policy.

Lifecycle: per-session. Created at casting, destroyed at end (memory may persist).
Layer 3

Runtime

The execution backend that produces the actor's responses. OpenAI, Anthropic, local LLM, a human at a keyboard, a Claude Code session, an external agent.

Lifecycle: connected per-actor. May multiplex many actors.
Critical idea

The human is just another runtime. No special case in the protocol. The HumanRuntime adapter exposes an input box and streams typed characters as actor.chunk events. The session can't tell the difference.

Same goes for Claude. A ClaudeCodeRuntime adapter briefs a Claude Code session with the persona spec + context, lets it generate, streams chunks back. From Ensemble's perspective, Claude is just an actor that happens to be backed by Claude.

§2The actor protocol

Wire format: WebSocket + JSON messages. One WebSocket per actor connection. Bi-directional, streaming, low ceremony.

Why not WebRTC

WebRTC data channels would work, but the value-add (NAT traversal, low-latency media) is irrelevant for text. WebSocket is simpler, debuggable in DevTools, and every LLM SDK speaks it natively. We can add WebRTC later if we want voice personas.

Why not raw MCP

MCP has the right vibe — bidirectional, streaming, tool-call semantics. But MCP is structured client→server; the actor protocol is genuinely peer-to-peer. We may converge later. For now: plain WebSocket with our own message shape, stealing MCP's tool-call schema where useful.

Connection lifecycle

Actor →   Session:  actor.hello       { persona_id, runtime_type, runtime_version, capabilities }
Session → Actor:    session.brief     { session_id, seat_id, persona_spec, cast, scenario, history }
Session → Actor:    session.event*    // zero or more, until your turn
Session → Actor:    session.take_turn { turn_id, context_hint? }
Actor →   Session:  actor.chunk*      { turn_id, delta }
Actor →   Session:  actor.finalize    { turn_id, full_text, tools_used }
Session → Actor:    session.event*    // other turns happen
...
Session → Actor:    session.end       { transcript_url }

actor.hello declares what runtime this is and what capabilities it offers (tool use, memory, streaming, buzz-in). The session can decline an actor that doesn't meet template requirements.

Session → Actor messages

MessagePayloadWhen

session.cooldown{ rounds: N, reason }moderator put you on cooldown

MessagePayloadWhen

actor.finalize{ turn_id, full_text, tools_used }turn complete

Moderator extensions privileged

The moderator is also an actor, but it has additional outbound messages. Server-side validated based on seat role + moderation config.

MessageEffect
mod.force_speaker{ seat_id } — next turn goes to that seat regardless of mode
mod.cooldown{ seat_id, rounds, reason } — put a seat on cooldown
mod.bypass{ seat_id, reason } — skip seat this round
mod.inject{ turn_id } — moderator speaks now, ahead of queue
mod.edit_memory{ seat_id, key, value } — mutate another actor's memory (audited in transcript)
mod.invoke_tool{ tool, args } — call a tool visibly to the cast

§3Runtime adapters

A runtime adapter translates between the actor protocol and a specific execution backend. Adapters are server-side processes (or threads) that hold a WebSocket to the session and an SDK/connection to the backend.

AdapterBackendNotes
OpenAIChatAdapterOpenAI Chat Completions / Responses APIStandard. Builds messages from brief + accumulating events.
AnthropicChatAdapterAnthropic Messages APISame shape; system slot for persona prompt.
LocalLLMAdapterOllama / vLLM / llama.cpp (OpenAI-compatible)Same as OpenAI adapter, different base URL.
HumanAdapterText box in the Ensemble UIOn take_turn, focus input. Stream typed characters as chunk. finalize on submit.
ClaudeCodeAdapterClaude Code subagent(stretch — see below)

The Claude Code adapter — the killer demo

The user opens a Claude Code session, runs /ensemble join <session_url> as <persona_id>, and Claude Code connects as that persona. Each take_turn fires a focused subagent call (or a turn-scoped Claude call) with the persona prompt + session history; the subagent's streaming output becomes chunk events.

Why this is the killer demo

Claude can join any session as any persona without any code changes to Ensemble itself. The Persona/Actor/Runtime split exists precisely so this works.

Two implementations to weigh:

  1. Slash command + MCP server. Ensemble exposes an MCP server. Claude Code adds it. /ensemble join calls a tool that opens the WebSocket. Standardized, but MCP's client→server bias makes bi-directional awkward.
  2. Standalone client invoked by Claude Code. Small Node/Python binary ensemble-actor. Cleaner protocol, requires install.

Probably (1) for v1 — MCP is becoming the lingua franca.

Future adapters

  • ExternalAgentAdapter — generic webhook for LangGraph, CrewAI, AutoGen, etc.
  • RecordedAdapter — plays back canned responses; testing and demos.
  • VoiceAdapter — TTS + STT bridge. Personas you can actually talk to.

§4Turn-taking modes (v1 scope)

You confirmed: ship four modes in v1. Interruption and hybrid deferred.

ModeMechanic
round-robinFixed order across rounds. Standup-style.
shuffledReshuffled order each round. Default in both baselines.
host-drivenOne designated Host seat picks who speaks next. Implementation: after each turn, the host gets a session.host_pick message; their response routes the next take_turn.
pollSelf-select with buzz-in. See below.

Poll mode and the buzz-in policy

Mechanic:

  1. After each turn, the speaker enters a cooldown for cooldown_rounds (default 1).
  2. For each idle, non-cooldown seat, the session sends session.buzz_check with the last 1–3 turns.
  3. Each actor returns actor.buzz_response with { score: 0–10, intent, can_pass }.
  4. Highest score wins. Quiet-bias optional. Tie-break random.
  5. The winner's intent becomes a hint in their subsequent session.take_turn.
The meta-cognitive piece

Each persona spec includes a buzz_in_policy — a short natural-language description of when this persona wants to speak:

"Buzz in when factual claims are being made without evidence, or when someone is conflating routing with retrieval. Stay quiet when the conversation is on strategy or org structure — that's not my area."

This policy is injected into the buzz-check prompt so the persona scores itself against its own meta-rules. It's the spec saying "here's what playing me well looks like — and here's how to know when to be quiet."

can_pass: false lets a persona signal "I don't have anything useful here, skip me entirely this round."

§5Memory

Every actor has a memory store. Scope set by persona.memory_policy:

PolicyBehavior
ephemeralLives during the session, discarded on end.
session-scopedPersisted with the session transcript, reloadable if you re-open it.
persistentSynced to the persona's global memory across all sessions.

Operations: read(key) → value, write(key, value), list() → keys[]. The actor uses actor.memory_op; the session confirms with session.memory_synced. Moderator can mutate any actor's memory with mod.edit_memory (audited in the transcript).

UI surface: each actor's row in the session UI gets a memory affordance — a notebook icon that opens an editable key-value panel. Useful for inspection, debugging, scripting scenarios where you want to seed a persona with prior knowledge.

§6Tools

Persona spec declares tools_allowed: [...]. The session validates each actor.tool_call against this allowlist.

v1: only the moderator (in its fact-checker role) gets web_search. Cast personas have tools_allowed: [].

Future: any persona can declare tools. A researcher persona with web_search + arxiv_search; a coder persona with code_execute + read_file; a trader persona with quote_lookup.

Tool execution is session-mediated. The session receives actor.tool_call, invokes the tool, returns session.tool_result. Slow tools (search) stream interim status via session.event { kind: "tool_status" } so the UI can render the "🔍 Searching: …" indicator from the baseline.

§9Open questions

  1. Server-side vs. client-side LLM adapters. Server-side (Ensemble holds keys, eats the bill) or client-side (browser holds keys, talks direct to OpenAI)? Probably: server-side default, BYO-key option.
  2. WS per actor vs. multiplexed. One WS per actor is clean. Multiplexing across actors backed by the same provider scales better. v1: one per actor.
  3. Buzz-in cost. N small LLM calls per turn in poll mode. At 5 personas × 30 turns × $0.001 ≈ $0.15 overhead. Flag if painful.
  4. Buzz-in fidelity. Does the buzz score reflect what the persona would say, or just whether they want to say something? Worth testing whether polled intent matches eventual turn.
  5. Memory key namespacing. If a persona is in two sessions simultaneously with session-scoped memory, do they collide? Probably namespace by (persona_id, session_id).
  6. MCP vs. custom protocol convergence. Worth a real spike before v1 to see how painful pure-MCP would be. If tolerable, we get Claude Code integration for free.
  7. "Claude joins as Keith" UX. A slash command? A new top-level command? An invisible MCP that just receives a brief? — separate from the protocol design.

§10Why this split matters (beyond Ensemble)

The Persona / Actor / Runtime split isn't Ensemble-specific. It's a general way to express "a configured cognitive role that can be hosted in any execution substrate." Once you have it:

  • The same persona library works across products.
  • New runtimes (local models, specialized agents, voice avatars) plug in without rewriting consumers.
  • Memory becomes inspectable and editable — a debugging surface, not just an internal blob.
  • The human and the model are symmetrically treated, which is the right default for HITL workflows.

Treat Ensemble as the first concrete consumer of this abstraction. If the protocol is clean here, it's reusable.
