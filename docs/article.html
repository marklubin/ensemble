Ensemble · Long-form

A pluggable runtime architecture for multi-persona sessions.

A persona is a specification, not an implementation. The runtime is who's at the controller. The contract between them is two thin interfaces in opposite directions, and the rest of the system follows from that.

May 2026 · Mark Lubin

What Ensemble is

Ensemble is a web app for running multi-persona scene simulations — debates, roundtables, interviews, writers' rooms, mock trials. You assemble a cast of personas, hand them a scenario, and watch them play it out as a live screenplay-style transcript. Each persona has its own voice, role, and behavior. Some sessions have a moderator who summarizes and fact-checks. Some sessions have a human at the keyboard, who shows up as just another seat at the table. The scheduler decides whose turn it is; the personas respond in their own voices; the result is a readable transcript that — if it's working — feels less like LLM output and more like a scene.

A persona is a portable specification: a name, a system prompt, a role hint, a voice signature, a short policy describing when this persona wants to speak. That spec lives in a library, decoupled from anything that knows how to generate text. The implementation — the thing that actually produces the persona's responses — lives somewhere else. It might be a hosted agent service. It might be a local model. It might be a Claude Code session a user is running on their own machine. It might be a person at a keyboard.

The same session can mix all of those.

The pluggability problem

Most multi-agent tools bake in a single backend. Every persona runs on the same model, through the same chat-completions loop, with the same tool-call plumbing built into the app. That made sense when "LLM" effectively meant "an OpenAI API key." It doesn't make sense now.

Managed agent services from the major model providers are first-class: Anthropic's Managed Agents, OpenAI's Agents SDK, Letta's persistent agent platform. Claude Code is a usable agent runtime in its own right. Local models are good enough for many roles. The Model Context Protocol is becoming the common language for agents to call out to external capabilities. And one seat in any session might simply be a human at a keyboard, who behaves differently than any model but should still be a peer participant in the scene rather than an exception bolted onto a model-only system.

The architecture we want lets each persona pick its own runtime — not as a configuration option, but as a structural property of the system. A session where one seat runs on Managed Agents, another on Claude Code, another on a local Letta agent, and another on a person typing should require no special handling. Same session, four runtimes, one transcript.

This forces a question: what's the contract between the application and a runtime? Whatever it is, it has to be small enough that adding a new runtime is a few hundred lines of code, and complete enough that the application doesn't need to know which runtime is behind which seat.

Two interfaces

The contract has two halves, with traffic flowing in opposite directions.

SPI · what runtimes implement

Ensemble calls into this. Four operations: attach, take turn, buzz check, detach. Plus capability flags declaring what each instance supports.

Host API · what Ensemble provides

The runtime — and the persona inside it — calls into this. Served as MCP tools: buzzer, memory, session metadata, privileged moderator extensions.

The first half is the Service Provider Interface. This is what a runtime implements so Ensemble can call into it. When the scheduler decides it's a particular seat's turn, it calls a method on that seat's runtime; the runtime produces a streamed response; the scheduler receives it. The SPI is small — four operations — because the runtime is doing the actual work of holding conversation state, calling tools, and generating text. Ensemble doesn't reimplement any of that.

The second half is the Host API. This is what Ensemble exposes back to whatever's running inside the runtime. The persona's agent loop — whether that's a Managed Agents session, a Claude Code session, or any other MCP-speaking runtime — can call into the Host API as if it were calling any other tool. Through the Host API, the persona can buzz in to request a turn, read and write its own memory, query session metadata, or (if it's the moderator) reach for privileged operations like forcing a speaker or putting another persona on cooldown.

The Host API is served as MCP tools on a per-session endpoint. The runtime is given the URL and an auth token when it's first attached. That's the whole integration: tell the runtime "here's where Ensemble lives," and the runtime's native MCP support handles everything else.

This is the standard plug-in architecture pattern with a bidirectional contract — the Java/OSGi world calls it "SPI plus Host API," the WebAssembly Component Model calls the same shape "imports and exports." The names matter less than the property they describe: both sides expose what they offer, both sides consume what the other offers, and neither side needs to know the other's internals.

The four operations

The SPI is a runtime adapter's whole obligation. Four operations and a capability set.

Attach

Provisions a fresh instance of a persona inside the runtime. What "provisioning" means depends on the runtime: for Managed Agents, it opens a new Session against an Agent definition built from the persona spec. For Claude Code, it registers a slot in a channel coordinator that an externally-running Claude Code session will later connect to. For a human seat, it registers the seat with the web UI's input bridge. The return value is an opaque handle Ensemble uses to address that instance for the rest of the session, along with the set of capabilities this particular instance supports.

Take turn

The main operation. The scheduler calls it when it's the persona's turn to speak. The arguments are the handle and a list of events the runtime hasn't seen yet — turns by other personas since this instance last spoke, moderator messages, scenario changes. The runtime brings the persona up to date, produces a response, and streams it back chunk by chunk. Ensemble doesn't dictate how the response is composed; it just consumes the stream and renders it to the transcript.

Buzz check

The polling mechanic for poll-mode turn-taking. In poll mode, between turns, the scheduler pauses and asks every idle, non-cooldown persona a single question: given what just happened, do you want to speak? The runtime returns a score from zero to ten, a one-sentence statement of intent describing what the persona would contribute, and a flag indicating whether the persona is willing to pass entirely. The scheduler picks the highest scorer; that intent then becomes a hint passed back to the winner on the next take-turn call, which keeps them honest to what they signaled they'd say.

Detach

Cleans up the instance at session end. For runtimes that bill per session-hour, this matters operationally. For ephemeral runtimes, it's a no-op.

The capability flags declare what an instance supports: streaming, buzz checks, tool calls, MCP, memory inspection, pause/resume. A session that needs a feature an instance doesn't support either degrades gracefully or refuses to cast that runtime in that role. A human seat, for instance, declares only streaming — it can't answer a programmatic buzz check, so poll-mode sessions surface a "buzz in" button in the UI for the human instead.

The host's tool surface

The Host API is the surface a persona's agent can call into. It's organized into four groups of tools.

Turn signaling is how a persona influences when it speaks. buzzer.press takes an intensity score and a one-sentence intent — it's the response to a buzz check, and it's also how a persona can request an out-of-turn interjection. buzzer.pass declines a turn explicitly, which the scheduler honors by skipping that seat this round.

Memory is read/write/list on a key-value store scoped to the persona's seat in this session. The store lives on Ensemble's side, not inside the runtime. This is deliberate: memory survives runtime swaps, can be inspected from the UI (and edited, eventually), and doesn't depend on whether the underlying runtime has its own memory features. A persona's working memory is a first-class artifact of the session, not an opaque internal detail of whatever's generating its responses.

Session metadata gives the persona context about its situation. cast.list returns who else is in this session and what role each plays. round.info returns the current round number, the turn-taking mode, and the persona's cooldown status. These let the agent reason about where it is in the scene without Ensemble baking everything into the system prompt.

Moderator extensions are privileged tools only available to a seat with the moderator role. Server-side validation enforces this via claims in the MCP token issued at attach time. The moderator can force a specific seat to speak next, put a seat on cooldown for several rounds, bypass a seat this round entirely, or inject itself into the conversation ahead of the queue. These aren't a separate command channel — they're tools the moderator's agent can choose to call when its judgment says the conversation needs steering.

Three runtimes that prove the abstraction

The architecture is only as honest as the runtimes that implement it. The v1 release ships three.

Anthropic — managed-agents

The primary cast runtime. The runtime auto-detects between Anthropic's beta Managed Agents API (which exposes a stateful Session keyed off a server-side Agent definition) and a DirectSdkRuntime fallback that uses regular messages.create with a manual tool-use loop. Both wear the same registry name, so the rest of the system doesn't see the difference. When the Managed Agents beta surface stabilizes, the fallback retires; the SPI doesn't change.

Claude Code — pair coding via channels

An externally-managed Claude Code session — one a user is already running in their terminal — can join an Ensemble conversation as a seat at the table. The mechanism is Claude Code's recently-introduced channels feature: a small MCP server (distributed as a Claude Code plugin) is registered in the user's configuration; when they launch Claude with channels enabled, the bridge connects back to Ensemble's main server over WebSocket. Turns are pushed into Claude as notifications/claude/channel events; Claude responds by calling a reply tool the bridge exposes, which streams the response back to Ensemble.

The result is genuine pair-coding-style collaboration. The user keeps working in Claude. Their Claude joins a session, speaks when it's its turn, calls Host API tools when appropriate, and returns to whatever the user was doing before. Two-way, no per-turn subprocess churn, no fragile state synchronization — the session is held by the runtime, and Ensemble just orchestrates turns.

Human — first-player UI

A person at a keyboard. From the SPI's perspective, indistinguishable from any other runtime — the operations have the same shape; only the implementation differs. Attach registers the seat with the UI bridge. Take turn focuses the input field and streams typed characters back to the scheduler as they're entered. The "stream" is literal: other personas in the session see the human's words appearing in real time, identical to how a model-backed persona's response would appear. Buzz check returns a no-buzz response — humans don't respond on demand to a programmatic poll. The UI separately surfaces a "buzz in" button that calls buzzer.press directly on the Host API, which keeps the mechanic available without forcing the symmetry where it doesn't fit.

Why this design

An earlier draft of the runtime contract defined a custom WebSocket protocol with granular wire-level messages: streaming chunks, tool-call requests, memory operations, capability negotiation. It was wrong in a specific way. It assumed Ensemble would reimplement the chat loop, tool dispatch, and memory plumbing that every modern agent runtime already provides. Every adapter would have spent its time translating between Ensemble's primitives and the runtime's native ones — twice the work, twice the surface area to maintain, and worse ergonomics than just using the runtime's own tooling.

The current design moves the chat loop into the runtime, where it belongs, and pushes everything Ensemble needs from the persona side onto MCP — a protocol every relevant agent runtime already speaks. The SPI is four operations. The Host API is a dozen tools. Each operation does one thing.

A few specific decisions fell out of this. Memory lives on the host side, not inside the runtime. This means memory is portable across runtime swaps, inspectable from the UI, and doesn't depend on any particular runtime having its own memory features. Streaming is just an async iterable of strings. No framing, no metadata, no protocol overhead. Every backend natively produces one; the adapter is just a yield loop. The buzzer is a tool, not a wire-level primitive. A persona's "buzz-in policy" — a short natural-language description of when this persona wants to speak — becomes guidance for when the agent should call the buzzer tool, rather than a special protocol mechanic. Moderator powers are tools too. There's no privileged command channel between the moderator and the scheduler; the moderator's agent just has a few extra tools it can call, gated by the claim baked into its MCP token.

What this enables

The immediate result is that v1 ships with two runtime adapters in tested production state — Anthropic and Human — plus the Claude Code channel runtime as the v1.5 deliverable. The architecture accepts a fourth, fifth, and sixth without rearchitecting. A v2 release can add a Letta adapter, an OpenAI Agents SDK adapter, a local-models-via-Ollama adapter — same scheduler, same UI, same Host API, different runtimes per seat.

The longer-term result is that persona definitions become portable. The same persona library can power any product that wants to embody those characters. Memory becomes a first-class inspectable artifact. The boundary between system and persona stays clean. And the human is a peer participant in the scene rather than a special case bolted onto a model-only architecture.

The contract is small because the runtimes are doing the work. The work was already being done; the only thing missing was the right boundary to do it across.
